Remarks

The window is a hidden top-level WS_POPUP window with WS_EX_TOOLWINDOW, it is deliberately NOT a message-only (HWND_MESSAGE) window: only top-level windows receive broadcasts like WM_QUERYENDSESSION, WM_POWERBROADCAST, WM_DISPLAYCHANGE and WM_SETTINGCHANGE.

The window is created lazily on first use (the first access to Handle, Messages, Listen(Action<nint>, Action<nint>) or Invoke(Action<nint>)) and then lives until the process exits. If it is destroyed externally, or with Shutdown(TimeSpan?), it is recreated on the next use.

When the process exits (ProcessExit) the window is destroyed on its own thread with Shutdown(TimeSpan?), so Windows sends WM_RENDERALLFORMATS and WM_DESTROYCLIPBOARD and delayed rendered clipboard content survives the process. From then on the window is not created again, see IsProcessExiting.

On .NET Framework, in an AppDomain which is not the default AppDomain (e.g. a test host), the same happens on DomainUnload: the window is destroyed and its thread ends before the CLR aborts the threads of the unloaded AppDomain. On .NET (Core) there is only one AppDomain, there nothing changes.

Registrations which need a window handle and must happen on the thread of that window (clipboard format listener, session notifications, raw input, device notifications, ...) should use Listen(Action<nint>, Action<nint>) with an onSetup and onTeardown action, or Invoke(Action<nint>).

Remarks

OnNext is called synchronously inside the window procedure, on the window thread. Handled and Result are only honoured when set synchronously in OnNext, if any subscriber sets Handled the window procedure returns Result, otherwise the default window procedure is called. Subscribing makes sure the window exists, it never creates or destroys windows otherwise. The sequence never completes. An exception thrown by a subscriber does not affect other subscribers or the message pump, it is published on SubscriberErrors (and, as usual in Rx, the throwing subscription is detached).

ProcessExitShutdownTimeout

The maximum time the automatic Shutdown(TimeSpan?) on ProcessExit waits, this includes the time the delayed clipboard renderers need (WM_RENDERALLFORMATS). Default is 1.5 seconds: on .NET Framework all ProcessExit handlers together only get about 2 seconds. The same timeout is used for the automatic shutdown on DomainUnload of a non-default AppDomain (.NET Framework).

Remarks

Destroying the window makes Windows send WM_RENDERALLFORMATS (when the window owns the clipboard) and WM_DESTROY / WM_NCDESTROY: the delayed clipboard renderers of Dapplo.Windows.Clipboard run synchronously on the window thread, before this returns. This is called automatically when the process exits (ProcessExit, with ProcessExitShutdownTimeout) and, on .NET Framework, when a non-default AppDomain is unloaded (DomainUnload), call it yourself when you want to control the moment, e.g. at the end of your Main.

After an explicit Shutdown the next use of the SharedMessageWindow creates a new window, but registrations which were made with Listen(Action<nint>, Action<nint>) or Invoke(Action<nint>) (clipboard listener, hotkeys, session notifications, ...) belonged to the old window and are gone: their onTeardown actions are not called anymore. Shutdown is meant for the end of the application. During process exit the window is not created again (IsProcessExiting).

Called on the window thread itself, the window is destroyed directly and the message loop ends when control returns to it.

ArgumentOutOfRangeException
