Read the text a window shows on the screen through UI Automation, as lines and words with their bounds and the targets of links: for windows whose text should not go through OCR (browsers, Electron, WPF, UWP, Office). Generic, nothing is specific to an application. Works on a window handle, so also while another window (a full-screen selection window) covers the window.

Remarks

The UI Automation calls run on a background (MTA) thread of the thread pool, the returned task completes with a snapshot. The control view of the window is read level by level (one FindAllBuildCache per element whose children are read, only the children which aren't offscreen, with a cache for the bounds, control type, name, value, password and TextPattern state).

An element with a TextPattern (a document of a browser, an edit field, a WPF RichTextBox, Word) is read with one request for its whole subtree (BuildUpdatedCache with TreeScope_Subtree). When that subtree has Text elements (browsers, Electron and WebView2 expose every run of text as one) the text comes from the elements: a few requests for the whole page instead of several per word through the TextPattern, which is slow in Chromium. Else the TextPattern is read line by line: per line its text and its rectangles, the words get their share of the line by characters. Lines with a link (a hyperlink element inside the element, located with TextPattern.RangeFromChild) are read word by word, so the words of the link get its target exactly.

Elements: a Text element is a run with its name and bounds (a hyperlink inside it is read too and, when it covers the whole text, replaces it), the Text elements inside a Hyperlink get the hyperlink's value (ValuePattern, the URL in a browser) as link target, a Hyperlink without Text elements is a run with its name, a single-line Edit element without TextPattern a run with its value. A run is split into words which get their share of the run's bounds by characters; a run which is higher than one and a half lines wraps: inside a document its line rectangles come from TextPattern.RangeFromChild, else it is cut into bands of a line. Words which overlap vertically are put on one line. The boxes are estimates, good for selections and labels.

Password elements (IsPassword) are left out with their children, also words of a TextPattern which lie in a password element. Offscreen elements are left out, and everything is clipped to its element, the window and area; a word with nothing left is left out.

Some applications (e.g. Chromium based browsers) build their accessibility tree only when a UI Automation client asks for it: while no text is found and the tree looks incomplete (the check of FindAreasAsync(nint, int, int, TimeSpan?, TimeSpan?, CancellationToken)), the text is read again with a pause of a quarter of a second, until it is found, the tree is complete or DefaultContentWait (at most maxDuration) has passed.

When maxDuration has passed the reading stops and the snapshot has the lines read until then, with TimedOut true. IsComplete is false when it stopped, gave up waiting for the tree, a request timed out, a limit was reached, the window is gone or UI Automation isn't available.

A window of a remote display client (Citrix Workspace app, Remote Desktop, Horizon, ..., see GetKind(nint)) is a picture for Windows, UI Automation has no text for the remote content: it is read once without waiting for the tree, IsComplete is false and RemoteDisplay says which client it is, so the caller knows it has to use OCR.

Where IUIAutomation2 is available (Windows 8+) the connection and transaction timeouts are set, so a hanging application can't block for the default 20 seconds. Neither text nor link targets are logged, only counts and timings (at verbose level, per phase, with the number of UI Automation requests).
