# Dapplo.Windows code review (September 2026)

Reviewed: `master` at `6a01652`: all 23 library projects, tests, examples, build/CI, README, `doc/` and `wiki/` (about 50k lines).
This was a static review; nothing was compiled during it. Findings marked *needs-runtime-check* are real on reading but should be confirmed on Windows.

**239 findings:** 6 Critical, 40 High, 86 Medium, 69 Low, 38 Quirk. 56 of the fixes are breaking changes.

Finding IDs are prefixed by area: A = User32/core, B = Input/Messages, C = Common/Gdi32/Icons, D = Clipboard/Com/Kernel32/Dpi, E = smaller packages, F = build/tests/docs.
Known overlaps: E-02 has the same root cause as B-01, F-01 duplicates B-05, F-36 duplicates C-15, F-35 overlaps E-33.

## Fix these first

1. **HRESULT checks are dead code** (C-01, C-07). `HResult` is a `uint` enum, so `Failed()` can never be true; every COM/DWM/DPI failure passes as success.
2. **Message results never reach Windows** (B-01, E-01, E-02). `WindowMessage` is a `record struct`, so subscribers set `Handled`/`Result` on a copy. The end-session reply is also inverted, so both must be fixed together or shutdown gets blocked.
3. **The clipboard can lock up for the rest of the process** (D-01). A failed `OpenClipboard` or a cancellation never releases the semaphore.
4. **Icon and cursor handles are double-freed** (C-02, C-03). Recycled handle numbers can then delete Greenshot's own bitmaps.
5. **Window enumeration can hang or crash** (A-04, A-03, A-02): blocking `SendMessage` to hung windows, an unbounded `stackalloc` sized by another process, and `|` instead of `&` in `Fill()`.
6. **`MonitorFrom` values are rotated** (A-01). "Nearest" is actually "null".
7. **The SharedMessageWindow handle is 0 until someone subscribes** (B-02, D-02).
8. **Input bugs users notice** (B-05, B-03, B-04): `TriggerOnKeyUp` never fires and leaves a stuck key, `MouseMove` normalises twice, and tick maths breaks after 24.9 days of uptime.
9. **Subscriber exceptions inside hooks and WndProcs kill the process** (B-06, B-09).
10. **The DPI context is pointer-sized but modelled as `int`, and the thread DPI scope leaks** (D-07, D-08, D-09).

## Plan: one 3.0 release in four passes

Decided on 29 Sep 2026:
- targets are `net480;net10.0-windows` only;
- `WindowMessage` becomes a sealed class;
- the WinForms and WPF helpers move out of Common into separate packages;
- work happens on branch `release/3.0`, and breaking changes are fine when they make the API right;
- every fix updates `CHANGELOG.md` and `doc/articles/migration-3.0.md`.

## A: User32 and core (Dapplo.Windows)

### A-01

**`MonitorFrom` enum values are all wrong (NULL, PRIMARY and NEAREST are rotated)**  
*High · BREAKING*

- **File**: `Dapplo.Windows.User32/Enums/MonitorFrom.cs`
- **What's wrong**: The code has `DefaultToNearest = 0, DefaultToNull = 1, DefaultToPrimary = 2`. Win32 (winuser.h) defines `MONITOR_DEFAULTTONULL = 0`, `MONITOR_DEFAULTTOPRIMARY = 1` and `MONITOR_DEFAULTTONEAREST = 2`. The enum also has `[Flags]`, but these values are not flags.
- **Failure scenario**: Every caller that asks for "nearest" gets "null". This includes `AppQuery.AppVisible` (App/AppQuery.cs:138), `NativeDpiMethods` (Dapplo.Windows.Dpi/NativeDpiMethods.cs:106 and 138), and any Greenshot code that uses the enum. For a window or rect that lies outside every monitor (off-screen, minimized at -32000, or on a monitor that was just unplugged), `MonitorFromWindow` and `MonitorFromRect` return NULL instead of the nearest monitor. The DPI lookup then fails or falls back to 96 DPI. Callers that pass `DefaultToNull` get the primary monitor instead of NULL, so "is it on any monitor?" checks can never fail.
- **Fix**: `DefaultToNull = 0, DefaultToPrimary = 1, DefaultToNearest = 2`, and remove `[Flags]`.
- **BREAKING**: yes. The numeric values change, and callers' behaviour silently becomes correct.

### A-02

**`Fill()` uses `|` instead of `&`, so ForceUpdate and AutoCorrect are always on and caching never works**  
*High · BREAKING*

- **File**: `Dapplo.Windows/Desktop/InteropWindowExtensions.cs:60, 61, 87`
- **What's wrong**:
  ```csharp
  var forceUpdate = (retrieveSettings | InteropWindowRetrieveSettings.ForceUpdate) != 0;       // always true
  var autoCorrect = (retrieveSettings | InteropWindowRetrieveSettings.AutoCorrectValues) != 0; // always true
  if ((retrieveSettings | InteropWindowRetrieveSettings.Maximized) != 0)                       // always true
  ```
- **Failure scenario**:
  - Every `Fill()` re-queries every property, which makes the whole cached-property design useless.
  - `AutoCorrectValues` cannot be switched off, so the DWM extended-frame-bounds correction and the parent intersection are always applied.
  - `IsZoomed` is called even when Maximized was not requested.
  - `ForceUpdate` also cascades into `GetChildren(true)`, `GetZOrderedChildren(true)` and `parent.GetInfo(true)`, so each `Fill` re-enumerates child windows. This is expensive when Greenshot enumerates all windows for the capture picker.
  - `Dump()` calls `Fill` and inherits the same problem.
- **Fix**: Use `&` in all three places.
- **BREAKING**: behavioural. Callers that relied on the accidental always-refresh will now see cached values unless they pass `ForceUpdate`.

### A-03

**`GetTextFromWindow` uses `stackalloc` with a size that another process controls, so a large text crashes the process**  
*High*

- **File**: `Dapplo.Windows.User32/User32Api.cs:240-257`
- **What's wrong**: `size` comes from `WM_GETTEXTLENGTH` sent to an arbitrary, possibly foreign, window. The code then runs `stackalloc char[size + 1]` with no upper bound.
- **Failure scenario**: The target is an Edit or RichEdit control holding about 500k characters or more, for example Notepad's edit child with a large file, or a log viewer. `stackalloc` then asks for more than 1 MB on the default thread stack. The result is a `StackOverflowException`, which cannot be caught and kills the process. This path is reachable through `IInteropWindow.GetText()` and through `Fill()` with `Text`. `Text` is part of `CacheAll`, `CacheAllWithChildren` and the default `CacheAllAutoCorrect`, and `Dump()` over children uses those settings.
- **Fix**: Use `stackalloc` only below a small threshold (for example 512 characters). Otherwise use `ArrayPool<char>` or a heap `char[]`. Also cap the size.
- **BREAKING**: no.

### A-04

**`GetText` / `Fill` use a blocking `SendMessage` to foreign windows, so one hung application freezes enumeration**  
*High*

- **File**: `Dapplo.Windows.User32/User32Api.cs:243, 254, 267`. Called from `InteropWindowExtensions.GetText` (line 343) and from `Fill` (Text is in every `CacheAll*` preset).
- **What's wrong**: `WM_GETTEXTLENGTH`, `WM_GETTEXT` and `WM_GETTITLEBARINFOEX` are sent with plain `SendMessage`, which has no timeout. `SendMessage` to a window whose thread is hung blocks forever. The library already has `TrySendMessage` built on `SendMessageTimeout` with `SMTO_ABORTIFHUNG`, but does not use it here.
- **Failure scenario**: Any hung application window makes `Fill()` block indefinitely. This hits Greenshot's window picker or capture-window list, and the capture never starts.
- **Fix**: Use `SendMessageTimeout(..., SMTO_ABORTIFHUNG | SMTO_ERRORONEXIT, ~500ms)` for all three calls. For `WM_GETTEXT`, the buffer marshalling is safe cross-process because the system marshals `WM_GETTEXT`.
- **BREAKING**: no. Text may come back empty or null for hung windows.

### A-05

**`WindowScroller` in `MouseWheel` mode can loop forever in `End()` and `Start()`**  
*High*

- **File**: `Dapplo.Windows/Desktop/WindowScroller.cs:192-201, 397-406` (with `IsAtEnd`/`IsAtStart` at 36-70 and `Next`/`Previous` at 293-297 and 329-333)
- **What's wrong**: The loop is `while (!IsAtEnd) { if (!Next()) break; }`.
  - `IsAtEnd` returns false whenever `GetScrollInfo` fails.
  - `Next()` in MouseWheel mode returns `MoveMouseWheel(...) == 1`, which is true whenever input was injected, whether or not anything scrolled.
  - `WheelDelta` can be 0. It is computed by integer division in `GetWindowScroller` (see A-17): with `PageSize = 2` and 3 wheel lines the result is 0.
- **Failure scenario**: A window whose scroll bar does not reflect wheel scrolling (browsers, Electron and most custom-drawn controls), a window that loses its scroll info, or a zero `WheelDelta`. Any of these gives an endless loop that floods the system with wheel input and hangs the calling thread.
- **Fix**: Add an iteration cap, and stop when the scroll position did not change between iterations. Guard against `WheelDelta == 0`.
- **BREAKING**: no.

### A-06

**`GetInfo(autoCorrect)` intersects owned top-level popups with their owner's bounds, because `GetParent` returns the owner**  
*High · BREAKING*

- **File**: `Dapplo.Windows/Desktop/InteropWindowExtensions.cs:220-226` (with `GetParent` at 239-253). The same concept is used in `InteropWindowQuery.IsTopLevel` and `IsPopup` (lines 119 and 172).
- **What's wrong**: Win32 `GetParent` returns the **owner** for a top-level window that has `WS_POPUP`. So `HasParent` is true for owned dialogs, message boxes, tool palettes and similar windows. `GetInfo` then clips their `Bounds` and `ClientBounds` to the owner's rectangle, which is only correct for real `WS_CHILD` windows.
- **Failure scenario**:
  - A dialog that extends past its owner window is cropped.
  - A dialog positioned entirely outside its owner gets empty bounds. `IsTopLevel` and `IsPopup` then reject it (`Bounds.IsEmpty`), so it disappears from window lists, and a Greenshot window capture of it comes out cropped or empty.
- **Fix**: Determine parenthood with `GetAncestor(hwnd, GA_PARENT)` (and compare it with `GetDesktopWindow()`), or check `WS_CHILD`. Expose the owner separately through `GetWindow(GW_OWNER)`.
- **BREAKING**: yes. The meaning of `Parent`/`HasParent` changes from "GetParent() result" to "real parent", and `Owner` should be added.

### A-07

**Imports without a CharSet bind to ANSI entry points (`SendMessageA`, `GetWindowLongPtrA`, `SetWindowLongPtrA`/`SetWindowLongA`), and the choice is inconsistent**  
*Medium*

- **File**: `Dapplo.Windows.User32/User32Api.cs:683-717, 752-776` (compare with 657-661)
- **What's wrong**: `[DllImport(User32)]` with no `CharSet` defaults to Ansi, and with ExactSpelling false the runtime resolves the missing plain name to the `…A` export. The results are:
  - The `SendMessage` overloads at 684, 695, 706 and 717 call **SendMessageA**, while those at 739 and 750 call SendMessageW.
  - `GetWindowLongPtr`, `SetWindowLongPtr` and `SetWindowLong` resolve to the A versions.
  - `GetClassLong` (32-bit) is declared `CharSet.Unicode`, so it resolves to **GetClassLongW**, but `GetClassLongPtr` (64-bit) resolves to **GetClassLongPtrA**. `GetClassLongWrapper` therefore changes charset depending on process bitness.
- **Failure scenarios**:
  - (a) `GetTextFromWindow` sends `WM_GETTEXTLENGTH` through SendMessageA, which returns the ANSI/DBCS byte length. It then sends `WM_GETTEXT` through SendMessageW and builds `new string(text, 0, size)` from the *ANSI* length, ignoring the character count the call actually returned. On CJK systems (DBCS code pages) the string has trailing `'\0'` characters. Docs: "WM_GETTEXTLENGTH ... may be greater than the actual length".
  - (b) `SetWindowLongWrapper(hWnd, GWL_WNDPROC, …)` calls the A version, so the new window procedure is registered as ANSI and receives ANSI-translated text messages.
  - (c) `GCLP_MENUNAME` returns an ANSI pointer on x64 but a Unicode pointer on x86.
- **Fix**: Give every text-sensitive import an explicit W entry point, for example `CharSet = CharSet.Unicode` or `EntryPoint = "SendMessageW", ExactSpelling = true`. In `GetTextFromWindow`, use the return value of `WM_GETTEXT` as the length.
- **BREAKING**: no (it is a behaviour fix).

### A-08

**`SetWindowStyle` throws `OverflowException` in 32-bit processes for `WS_POPUP`**

- **BREAKING**: no.

### A-10

**`ScrollBarInfo` has `xyThumbTop` and `xyThumbBottom` swapped, and `ThumbSize` is misnamed**

### A-11

**`GetCaption`'s deadlock guard protects the wrong case**  
*Medium · BREAKING*

- **File**: `Dapplo.Windows/Desktop/InteropWindowExtensions.cs:131-137` (doc at User32Api.cs:215-216)
- **What's wrong**: For a window owned by the current *process*, `GetWindowText` sends `WM_GETTEXT`. When the window belongs to the calling *thread*, that is a direct window-procedure call and cannot deadlock. A deadlock happens when the window belongs to **another thread of the same process** that is blocked waiting for the caller. The guard returns `string.Empty` for the safe case (same thread) and does nothing about the dangerous one.
- **Failure scenario**:
  - Greenshot's own UI-thread windows always report an empty caption. `IsTopLevel` therefore rejects them (`GetCaption().Length == 0`).
  - A caption query from a UI thread against a window on another thread of the same process, where that thread is blocked on this one, still hangs.
- **Fix**: For same-thread windows, just call `GetWindowText`. For windows on another thread of the same process, use `InternalGetWindowText` (reads the stored caption without sending a message) or `SendMessageTimeout(WM_GETTEXT)`.
- **BREAKING**: behavioural.

### A-12

**`WinEventHook`: thread affinity is not handled, the static dictionary is not thread-safe, and exceptions escape into the native callback**  
*Medium*

- **File**: `Dapplo.Windows/Desktop/WinEventHook.cs:24, 34-61`
- **What's wrong**:
  - (1) `SetWinEventHook(WINEVENT_OUTOFCONTEXT)` delivers events on the thread that subscribed, and that thread must pump messages. `UnhookWinEvent` "fails if called from a thread different from the call that corresponds to SetWinEventHook". With `.Publish().RefCount()`, the hook is installed on the first subscriber's thread and removed on whichever thread disposes the last subscription.
  - (2) `Delegates` is a plain static `Dictionary`, mutated from arbitrary subscribe and dispose threads.
  - (3) An exception thrown by `observer.OnNext` propagates into the native WINEVENTPROC.
  - (4) Every `Create()` or `WindowTitleChangeObservable()` call creates a separate hook; the sharing through `Publish().RefCount()` only happens if the caller caches the observable.
- **Failure scenarios**:
  - Subscribing from a thread-pool thread means no events are ever delivered.
  - Disposing on another thread makes `UnhookWinEvent` fail silently. The hook stays alive, and its delegate is removed from `Delegates`, so it can be garbage-collected while the hook is live. The next event then calls a collected delegate and crashes (CallbackOnCollectedDelegate).
  - Concurrent subscriptions corrupt the dictionary.
- **Fix**: Run the hook on a dedicated message-loop thread (or the `SharedMessageWindow` thread) and marshal subscribe and unsubscribe to it. Use `ConcurrentDictionary`. Wrap `OnNext` in try/catch and forward the error to `OnError`.
- **BREAKING**: no.

### A-13

**`GetTopWindows(parent)` yields a bogus window with handle 0 when the parent has no children**

### A-14

**`GetChildren` returns *all descendants*, but sets `ParentWindow` to the root for each of them**  
*Medium · BREAKING*

- **File**: `Dapplo.Windows/Desktop/InteropWindowExtensions.cs:152-169`, `Dapplo.Windows/Desktop/WindowsEnumerator.cs:53-72`

The docs say: "If a child window has created child windows of its own, EnumChildWindows enumerates those windows as well." `GetChildren` then assigns `child.ParentWindow = interopWindow` to every one of them. `GetZOrderedChildren` returns only direct children, so the two "Children" collections have different meanings.

### A-15

**`GetInfo` has a hidden side effect: `IsApp()` → `GetChildren()` overwrites `Children` and enumerates all descendants**  
*Medium*

- **File**: `Dapplo.Windows/Desktop/InteropWindowExtensions.cs:214`, `Dapplo.Windows/App/AppQuery.cs:215, 228`
- **What's wrong**: On Win10+, for every top-level window where DWM frame bounds succeed, `GetInfo` calls `IsApp()` → `IsWin10App()` → `interopWindow.GetChildren()`. That call does a full descendant enumeration and **replaces** `Children` with the non-Z-ordered list, setting `HasZOrderedChildren = false`. The same happens in `IsTopLevel` and `IsPopup` through `IsBackgroundWin10App`.
- **Failure scenario**:
  - A caller runs `GetZOrderedChildren()` and later calls `GetInfo(forceUpdate: true)`. Because of A-02, that is every `Fill`. The Z-ordered children are silently replaced by unordered descendants.
  - It is also a large performance cost: browsers and Office windows have hundreds of descendants, and they are enumerated for each window on each `Fill`.
- **Fix**: In `IsWin10App`, check the class name of the window and use `FindWindowEx(hwnd, 0, "Windows.UI.Core.CoreWindow", null)` without touching the cached `Children`.
- **BREAKING**: no.

### A-16

**`PrintWindow<T>` sizes the bitmap from DWM extended frame bounds, but `PrintWindow` draws from the full window rect**  
*Medium · needs-runtime-check*

- **File**: `Dapplo.Windows/Desktop/InteropWindowExtensions.cs:718-735` (with `GetInfo` autoCorrect at 210-217)
- **What's wrong**: On Win10+, for non-maximized windows `GetInfo().Bounds` is replaced by `DWMWA_EXTENDED_FRAME_BOUNDS`, which excludes the invisible resize borders of about 7 px. `PrintWindow(PW_COMPLETE)` renders the window DC with its origin at the full `GetWindowRect` origin, which includes those borders.

- **Fix**: Allocate the bitmap from the raw `GetWindowRect` size, print into it, then crop to the extended frame. Consider `PW_RENDERFULLCONTENT` (0x2).
- **BREAKING**: no.

### A-17

**The `WheelDelta` calculation can divide by zero, produce 0 or a negative value, and mixes units**  
*Medium*

- **File**: `Dapplo.Windows/Desktop/InteropWindowExtensions.cs:370, 383`, `Dapplo.Windows/Desktop/WindowScroller.cs:108-126`
- **What's wrong**: `(int)(120 * (PageSize / ScrollWheelLinesFromRegistry))` does integer division (`uint / int` → `long`).
  - With `WheelScrollLines = "0"` it throws `DivideByZeroException`.
  - With `"-1"` (WHEEL_PAGESCROLL) the result is negative.
  - With `PageSize < lines` the result is 0.
  - `PageSize` is in scroll units while wheel lines are text lines, so the formula is not meaningful.
  - The value is read from the registry instead of `SystemParametersInfo(SPI_GETWHEELSCROLLLINES)`.
- **Failure scenario**: A user who set wheel lines to 0 gets an exception from `Fill()` on any scrollable window, because ScrollInfo is in `CacheAll`.
- **Fix**: Use `SPI_GETWHEELSCROLLLINES` and special-case 0 and `uint.MaxValue`. Default the delta to `WHEEL_DELTA` (120) multiplied by a sensible count.
- **BREAKING**: no.

### A-18

**`SafeCurrentInputDesktopHandle` has side effects in its constructor and cannot release its handle**  
*Medium · BREAKING*

- **File**: `Dapplo.Windows.User32/SafeHandles/SafeCurrentInputDesktopHandle.cs:22-56`
- **What's wrong**:
  - The constructor calls `SetThreadDesktop(hDesktop)` and never restores the previous desktop.
  - `ReleaseHandle` calls `CloseDesktop` on the desktop that is still the thread's current desktop. That fails because the desktop is in use by a thread of the process, so the handle leaks and `ReleaseHandle` returns false. `ReleaseHandle` can also run on the finalizer thread.
  - `fInherit = true` for no reason.
  - The `DesktopAccessRight.GENERIC_ALL` it requests is not `GENERIC_ALL` (0x10000000); it is the OR of the desktop-specific rights. Asking for JOURNALRECORD/JOURNALPLAYBACK/HOOKCONTROL often fails for normal users or on the secure desktop.

- **Fix**: Make it a plain SafeHandle around `OpenInputDesktop` with minimal rights and `fInherit = false`. Add a separate scope object that saves `GetThreadDesktop`, switches, and restores on dispose, before the handle is closed.
- **BREAKING**: yes (API shape).

### A-19

**The static `DisplayInfo` cache has a race that can return null and misses work-area changes**  
*Medium*

- **File**: `Dapplo.Windows.User32/DisplayInfo.cs:103-126, 73-97`
- **What's wrong**:
  - The getter reads `_allDisplayInfos` twice (check, then return), and the `WM_DISPLAYCHANGE` handler on the message-window thread sets it to null in between. `AllDisplayInfos` can therefore return **null**, and callers that `foreach` over it get a `NullReferenceException` (for example `GetBounds` and `ScreenBounds`).

## B: Input and Messages

### B-01

**`WindowMessage` is a value type, so the `Handled` and `Result` values set by subscribers are always lost**  
*Critical · BREAKING*

- **Where:** `Messages/Structs/WindowMessage.cs:17` (`public record struct WindowMessage(...)`), consumed in `Messages/SharedMessageWindow.cs:174-181`.
- **What:** The WndProc builds `var windowMessage = new WindowMessage(...)`, calls `observer.OnNext(windowMessage)` and then checks `windowMessage.Handled`. Because the type is a `record struct`, every subscriber gets a **copy**. Setting `windowMessage.Handled = true` or `.Result = x` inside a `Subscribe` lambda only changes the lambda parameter. The WndProc therefore always falls through to `DefWindowProc`, and no custom LRESULT is ever returned.
- **Failure scenario:**
  - `AppRestartManager/ApplicationRestartManager.cs:196-217` sets `Result` and `Handled` for WM_QUERYENDSESSION/WM_ENDSESSION. Both are ignored, so the app can never veto or acknowledge a shutdown.
  - `RawInputMonitor` and `RawInputDeviceMonitor` set `Handled = true`, which is also ignored. For WM_INPUT this is accidentally correct, because DefWindowProc must run there.
  - Any user code relying on `Handled` or `Result` silently does nothing. The C# compiler raises no warning because assigning to a struct lambda parameter is legal.
- **Fix:** Make it a `sealed record class`, or a class with mutable `Handled`/`Result`. Alternatively, pass a `ref`-capable holder. Once the class is in place, audit all consumers.
- **Side note (other group's scope, surfaced by this bug):** `ApplicationRestartManager` returns `HResult.S_OK` (0) for "can end session". For WM_QUERYENDSESSION, 0 means FALSE, which *blocks* shutdown. It becomes live the moment B-01 is fixed.
- **BREAKING:** yes. The type kind changes and value semantics and equality change.

### B-02

**The raw-input monitors register against `SharedMessageWindow.Handle` before the window exists**  
*Critical*

- **Where:** `Input/RawInputMonitor.cs:40-59`, `Input/RawInputDeviceMonitor.cs:49-73`, `Messages/SharedMessageWindow.cs:156-237`.
- **What:** Subscribing to `SharedMessageWindow.Messages` only *starts* a thread. The HWND is created asynchronously and published through `_handleSubject` later. On the next line, the monitors call `RawInputApi.RegisterRawInput(SharedMessageWindow.Handle, ...)`. Unless some other component already holds the shared window, `Handle` is still `0`.
  - `RawInputMonitor` passes `RIDEV_INPUTSINK` with `hwndTarget == NULL`. `RegisterRawInputDevices` fails with ERROR_INVALID_PARAMETER, and a `Win32Exception` is thrown from inside `Observable.Create`. The message subscription leaks, and the subscriber gets OnError or a throw.
  - `RawInputDeviceMonitor` passes `DeviceNotify` with NULL. Input then follows keyboard focus, which the invisible window never has, so no `WM_INPUT_DEVICE_CHANGE` arrives.
  - When the shared window is recreated (last subscriber gone, then a new one), nobody re-registers. Nothing is ever unregistered with `RIDEV_REMOVE` either.
- **Failure scenario:** In a fresh process, `RawInputMonitor.Listen(RawInputDevices.Keyboard).Subscribe(...)` throws, or delivers nothing. It works only "by luck" if, for example, `DisplayInfo` or the clipboard already started the window.
- **Fix:** Use `SharedMessageWindow.Listen(onSetup: hwnd => Register(hwnd, ...), onTeardown: hwnd => Register(RIDEV_REMOVE, hwndTarget: 0))`. Remove the direct `Handle` reads.
- **BREAKING:** no.

### B-03

**`MouseInput.MouseMove` normalises the coordinates twice, and the normalisation is imprecise and ignores the virtual-desktop origin**  
*High*

- **Where:** `Input/Structs/MouseInput.cs:77-86` (RemapLocation) and `:119-130` (MouseMove).
- **What:**
  - `MouseMove` calls `RemapLocation(location)`, which already multiplies by `65535 / Width`, and then multiplies **again** by `65535 / bounds.Width`.
  - `65535 / Width` is integer division. For width 1920 it gives 34 instead of 34.13, so the error reaches about 8 px at the right edge. For a 7680 px desktop it gives 8 instead of 8.53, an error of about 480 px.
  - With `MOUSEEVENTF_VIRTUALDESK`, 0 maps to `SM_XVIRTUALSCREEN`, but `bounds.X` and `bounds.Y` are not subtracted, so a monitor to the left of or above the primary shifts everything.
  - `MouseMove` also divides by `bounds.Width` even when the guard in RemapLocation detected 0, which throws DivideByZeroException.
- **Failure scenario:** `MouseInputGenerator.MoveMouse(new NativePoint(100,100))` on 1920x1080 gives dx = 100·34·34 = 115600, which is clamped, so the cursor jumps to the far right edge. Clicks with a location on multi-monitor setups land on the wrong spot.
- **Fix:** Normalise once: `dx = (int)Math.Round((x - bounds.X) * 65535.0 / (bounds.Width - 1))`, and the same for y. Remove the second multiplication in `MouseMove`.
- **BREAKING:** no.

### B-04

**Tick-count arithmetic breaks after 24.9 days of uptime (EventTime, LastInput*, Msg.Time)**  
*High*

- **Where:**
  - `Input/Keyboard/KeyboardHookEventArgs.cs:167`: `Environment.TickCount - TimeStamp`
  - `Input/Structs/LastInputInfo.cs:27`: `Environment.TickCount - _dwTime`
  - `Messages/Structs/Msg.cs:47`
- **What:** `int - uint` is promoted to `long`, not wrapped. Once `Environment.TickCount` goes negative (after 24.9 days) while the native `DWORD` tick is above 2^31, the difference is about −4.29e9 ms. `TimeSpan` is then −49.7 days, and `EventTime`/`LastInputDateTime` land about 49.7 days **in the future**. Wrap-around at 49.7 days has the same problem.
- **Failure scenario:** On a machine with 25+ days of uptime, `NativeInput.LastInputTimeSpan` is hugely negative, so idle detection breaks ("idle for −49 days"). Keyboard event timestamps are also wrong.
- **Fix:** `TimeSpan.FromMilliseconds(unchecked((uint)Environment.TickCount - tick))`, which uses modular uint subtraction. Use this helper in all three places.
- **BREAKING:** no.

### B-05

**`TriggerOnKeyUp` never fires with the default `CanRepeat=false`, and it swallows the key-up, which leaves a stuck key**  
*High*

- **Where:** `Input/Keyboard/KeyCombinationHandler.cs:107, 126-149`.
- **What:** On the key-up of a matched key, `isRepeat = AvailableKeys[i]`. That value is always `true` because the key was down, which `wasAllKeysDown` requires anyway. `isHandled` becomes true, and `keyboardHookEventArgs.Handled = true` is set (line 139-142). - **Failure scenario:** `new KeyCombinationHandler(Control, Menu, LeftWin, KeyT){ TriggerOnKeyUp = true }`, which is the exact sample in `doc/articles/input-handling.md`, has these effects:
  1. The subscriber never runs.
  2. The key-down of T was passed through, but the key-up is **blocked** in the low-level (LL) hook. The system key state keeps T down, so the foreground app sees a stuck key.
  The unit tests for this feature are commented out (`//[Fact]` at KeyboardHookTests.cs:364, 384, 417), which is consistent with them failing.

### B-06

**Exceptions thrown by subscribers inside native callbacks crash the process**  
*High*

- **Where:** `KeyboardHook.cs:48-50`, `MouseHook.cs:48-49`, and `SharedMessageWindow.cs:174-175`. All call `observer.OnNext` with no try/catch inside a reverse-P/Invoke callback (hook proc or WndProc).
- **What:** An exception from any subscriber propagates through user32 frames. On the dedicated SharedMessageWindow thread, it reaches the thread entry and is unhandled, which terminates the process. For the LL hooks it unwinds through `GetMessage` or `DispatchMessage` on the UI thread. That is undefined behaviour or a fail-fast on .NET Core.
- **Concrete triggers inside this scope:**
  - `RawInputDeviceMonitor` (see B-12)
  - `WindowsSessionListener` (see B-11)
  - `RawInputApi.GetDeviceInformation` throwing `Win32Exception` when a device vanishes between arrival and query
  - A KeyNotFound in any user `Where` filter
- **Fix:** Wrap the callback bodies in `try { ... } catch (Exception ex) { log; /* optionally observer.OnError via a Subject */ }` and always continue with CallNextHookEx or DefWindowProc.
- **BREAKING:** no.

### B-07

**`WinProcWindowsExtensions` disposes the WPF Window's own HwndSource on unsubscribe**  
*High*

- **Where:** `Messages/WinProcWindowsExtensions.cs:83-106, 118-125`.
- **What:** For the `Window` overload, `hWndSource = HwndSource.FromHwnd(windowHandle)` is the window's **own** HwndSource. The disposal lambda calls `hWndSource.Dispose()`, which destroys the HWND of the user's window.

### B-08

**`RawHID.bRawData` is declared as a pointer, but it is an inline array; HID input is never delivered**  
*High · BREAKING*

- **Where:** `Input/Structs/RawHID.cs:18-31` and `Input/RawInputMonitor.cs:46-48`.
- **What:** `RAWHID` is `{ DWORD dwSizeHid; DWORD dwCount; BYTE bRawData[1]; }`, a variable-length inline array. The struct declares `IntPtr _bRawData`, so `GetData()` reinterprets the first 4 or 8 data bytes as a pointer and runs `Marshal.Copy` from it, which causes an AccessViolation or returns garbage.
  - Separately, `RawInputMonitor` calls `GetRawInputData` with `out RawInput` and `size = sizeof(RawInput)`. For HID reports larger than the struct the call returns −1, and the event is silently dropped.
- **Failure scenario:** `RawInputMonitor.Listen(RawInputDevices.ConsumerAudioControl / GamePad / Joystick)` produces no events. Any `RawInput.Device.HID.GetData()` crashes.
- **Fix:** Query the size first (`pData = NULL`), allocate a buffer, and parse the header, the fixed part and the trailing bytes. Expose the HID data as `byte[]` on the event args.
- **BREAKING:** yes. The public `RawHID` shape and the `RawInputEventArgs` layout change.

### B-09

**The LL hook runs subscribers synchronously, and a slow subscriber gets the hook silently removed**  
*High · BREAKING*

- **Where:** `KeyboardHook.cs:44-59`, `MouseHook.cs:44-60`.
- **What:**
  - All subscriber work runs inside the hook proc. Since Windows 7, a hook that exceeds `LowLevelHooksTimeout` (at most 1000 ms on Windows 10 1709 and later, often around 300 ms) is **silently removed**, and there is no notification. The repo's own test `TestKeyHandler_Slow_Subscriber` sleeps 500 ms per event in `OnNext`.
  - `SetWindowsHookEx` failure (`hookId == 0`) is ignored, so the observable silently never fires.
  - The hook is installed on whatever thread subscribes. If that thread doesn't pump messages, every keystroke system-wide stalls until the timeout.
- **Failure scenario:** Greenshot's capture handler does work inside the subscription. After one slow capture, hotkeys stop working until restart.
- **Fix:** Keep in-hook work minimal. `Handled` must be decided synchronously, so do it through the `IKeyboardHookEventHandler`. Then hand events off with `ObserveOn`, or document it loudly. Check `hookId` and call `observer.OnError(new Win32Exception())`. Optionally host the hook on a dedicated pumping thread, like SharedMessageWindow.
- **BREAKING:** partly, if delivery becomes asynchronous. Setting `Handled` from `Subscribe` would stop working.

### B-16

**SharedMessageWindow teardown is wrong and can leak threads and windows, causing duplicate messages**  
*Medium*

- **Where:** `Messages/SharedMessageWindow.cs:164-245`.
- **What:**
  1. Disposal *posts* `WM_DESTROY`. That is a notification, not a request, so `DestroyWindow` is never called.
     - The loop quits while the window still exists, so `UnregisterClass` fails (ERROR_CLASS_HAS_WINDOWS). One GUID-named class leaks per cycle.
     - Subscribers never see WM_DESTROY/WM_NCDESTROY.
  2. If disposal happens before the thread has assigned `hwnd` (a fast subscribe then unsubscribe; `hwnd` is also a non-volatile cross-thread capture), nothing is posted. The thread and window live forever and keep calling `observer.OnNext`.
     - Rx `Publish()` reuses its single Subject across RefCount reconnects, so a later subscriber receives messages from **both** the leaked window and the new one.
  3. `RegisterClassEx` and `CreateWindowEx` results are unchecked. If `hwnd == 0`, the thread blocks in `GetMessage` forever and can never be stopped.
  4. `GetMessage` is declared `bool`, so a −1 error return loops forever.
  5. The docs say "sequence completes when the window is destroyed", but `OnCompleted` is never called.
- **Fix:**
  - Post a private message (or WM_CLOSE) and call `DestroyWindow` in the handler.
  - Keep a `volatile`/`Interlocked` hwnd plus a "dispose requested" flag checked after creation.
  - Check the Win32 results and return the error via `observer.OnError`.
  - Declare `GetMessage` as returning `int` and handle −1.
  - Call `OnCompleted` after the loop.
- **BREAKING:** no.

### B-17

### C-01

**`HResult` is a `uint` enum, so `Failed()` is always false and `Succeeded()` is always true**  
*Critical · BREAKING*

- **Where:** `Dapplo.Windows.Common/Enums/HRESULT.cs:12` (`enum HResult : uint`) and `Extensions/HResultExtensions.cs:21-35`
- **What:** `hResult < 0` compares an unsigned value with 0, so it can never be true. `hResult >= HResult.S_OK` is always true. `ThrowOnFailure()` never throws.
- **Where it breaks:** every caller in the solution treats failures as success:

  - `NativeDpiMethods.SetProcessDpiAwareness(...).Succeeded()` always reports success.
  - `DpiHandler:409` has the same problem.
- **Fix:** make `HResult : int`, using `unchecked((int)0x80004005)` literals. Alternatively, test the high bit: `((uint)hr & 0x80000000) != 0`. Also, `ThrowOnFailure` casts `(int)hResult`. With a uint enum in a checked Debug build, that cast throws `OverflowException` for any failure code. Switching to an int-based enum fixes this too.
- **BREAKING:** yes. The underlying type changes, and P/Invoke signatures that return `HResult` stay compatible.

### C-02

## D: Clipboard, Com, Kernel32 and Dpi

### D-01

**ClipboardSemaphore never releases the semaphore when OpenClipboard fails or the call is cancelled, so the clipboard stays locked for the rest of the process**  
*Critical*

- **Where:** `Dapplo.Windows.Clipboard/Internals/ClipboardSemaphore.cs:73-80` (sync), `:124-127`, `:139`, `:142-150` (async)
- **What:** `_semaphoreSlim.Wait/WaitAsync` succeeds, then OpenClipboard is retried. If every retry fails, the method returns `new ClipboardAccessToken { CanAccess=false, IsOpenTimeout=true }` without a dispose action and without `_semaphoreSlim.Release()`. In `LockAsync` there are two more leaks: the `IsCancellationRequested` break returns the same kind of token, and `Task.Delay(retryInterval, cancellationToken)` throws `OperationCanceledException` while the semaphore is held.
- **Failure scenario:** Another process holds the clipboard for more than about 600 ms (clipboard managers, RDP clipboard sync, Office, and Windows clipboard history all do this right after a change). After that single failure, the process-wide `static ClipboardLockProvider` semaphore is 0 forever. Every later `ClipboardNative.Access()`/`AccessAsync()` returns `IsLockTimeout=true` after 200 ms, until the app restarts. The wiki's "Retry Logic" example cannot recover from this.
- **Fix:** Release the semaphore on every path that does not return a working token. Use try/catch around the open loop, and release before returning an `IsOpenTimeout` token or rethrowing an OCE.
- **BREAKING:** no

### D-02

**The default owner hWnd is 0 whenever nobody is listening, which makes ClearContents followed by Set* fail and breaks delayed rendering**  
*High*

- **Where:** `Clipboard/Internals/ClipboardSemaphore.cs:38-42`, `:104-108`; `Messages/SharedMessageWindow.cs:68` (`Handle => _handleSubject.Value`, BehaviorSubject initialised to 0; the window only exists while something subscribes)
- **What:** The comment says "if the window is still being created, wait for it reactively", but the code does not wait. It takes `SharedMessageWindow.Handle`, which is `0` unless some subscriber currently keeps the shared window alive. The docs for OpenClipboard say: *"If an application calls OpenClipboard with hwnd set to NULL, EmptyClipboard sets the clipboard owner to NULL; this causes SetClipboardData to fail."* Delayed rendering also needs a real owner window to receive WM_RENDERFORMAT.

- **BREAKING:** no (behaviour only)

### D-03

**AccessAsync breaks the clipboard's thread affinity (open, use and close can run on different threads)**  
*High · needs-runtime-check*

- **Where:** `Clipboard/Internals/ClipboardSemaphore.cs:111` and `:139` (`ConfigureAwait(false)`), `:152-155` (CloseClipboard inside the dispose lambda)
- **What:** The clipboard is opened per thread: win32k records the opening thread, and GetClipboardData/SetClipboardData/EmptyClipboard/CloseClipboard from another thread fail with ERROR_CLIPBOARD_NOT_OPEN. After a contended `WaitAsync` or any `Task.Delay` retry, `OpenClipboard` runs on a thread-pool thread. The caller's `await AccessAsync()` then resumes on its own SynchronizationContext (the UI thread), which does not own the clipboard. `Dispose` calls `CloseClipboard` on whatever thread disposes. `IClipboardAccessToken`'s XML doc even says "only valid within the same thread or window".
- **Failure scenario:** On a WinForms UI thread, `using var c = await ClipboardNative.AccessAsync(); c.SetAsUnicodeString("x");` works when there is no contention. When the first OpenClipboard fails and the retry path runs, it throws `Win32Exception` (clipboard not open), and the pool thread keeps the clipboard open until some other thread's CloseClipboard fails. needs-runtime-check for the exact error codes.
- **Fix:** Do not use `ConfigureAwait(false)` in `LockAsync`. Better, do the OpenClipboard attempt synchronously on the caller's thread, with only the waits being async. Record the owning thread in the token and assert it in `ThrowWhenNoAccess`/`Dispose`.
- **BREAKING:** no

### D-04

### D-06

### D-07

### D-11

### E-01

**WM_QUERYENDSESSION result is inverted, so returning "allow" blocks shutdown (masked today by E02)**  
*Critical · BREAKING*

- **File:** Dapplo.Windows.AppRestartManager/ApplicationRestartManager.cs:196 and :204
- **What:** `windowsMessage.Result = canEndSession ? (nuint)HResult.S_OK : (nuint)HResult.S_FALSE;`. For WM_QUERYENDSESSION the window procedure must return TRUE (1) to allow the session to end and FALSE (0) to block it. S_OK is 0 (FALSE) and S_FALSE is 1 (TRUE), so the mapping is exactly backwards. For WM_ENDSESSION the return value should simply be 0; there is no allow or block.
- **Failure scenario:** The FormsExample (Program.cs:34) passes `onQuerySession: _ => true`. That writes 0 (FALSE), which tells Windows or the Restart Manager that the app refuses to close. Windows shows "This app is preventing shutdown", and the Restart Manager escalates to a forced kill, so the app loses its state. This does not happen today only because of E02 (the result never reaches the window procedure). If the SharedMessageWindow struct-copy bug gets fixed on its own, this becomes a live shutdown blocker.
- **Fix:** For QUERYENDSESSION return `canEndSession ? 1 : 0`, and for ENDSESSION always 0. Do not use HResult for a BOOL/LRESULT. Give the ENDSESSION callback an `Action<bool /*ending*/, EndSessionReasons>` instead of `Func<...,bool>`.
- **BREAKING:** yes (the onEndSession callback signature changes).

### E-02

**Handled/Result can never propagate because WindowMessage and EndSessionMessage are `record struct`s passed by value**  
*High · BREAKING · Same root cause as B-01*

- **Files:** Dapplo.Windows.AppRestartManager/ApplicationRestartManager.cs:186-219 and Structs/EndSessionMessage.cs:16. Root cause is in Dapplo.Windows.Messages/Structs/WindowMessage.cs:17 together with SharedMessageWindow.cs:174-180.
- **What:**
  - SharedMessageWindow does `observer.OnNext(windowMessage); if (windowMessage.Handled) ...`, but `WindowMessage` is a struct, so every subscriber gets a copy and `Handled`/`Result` on the local is always false/0.
  - Inside ListenForEndSession the lambda sets `windowsMessage.Result/Handled` on its own parameter copy.
  - The same thing happens again one level down: `observer.OnNext(endSessionMessage); if (endSessionMessage.Handled)` checks a `record struct` copy, so subscribers setting `Handled`/`Result` have no effect.
- **Failure scenario:** No caller can ever block or answer WM_QUERYENDSESSION. The documented "return false to block" does nothing, and DefWindowProc always returns TRUE. There is also a knock-on effect: when an `onQuerySession` callback is supplied, the lambda sets its local `Handled = true`, so observers of the returned stream never see WM_QUERYENDSESSION/WM_ENDSESSION. In the FormsExample the `.Subscribe(...)` never fires for those messages.
- **Fix:** Make WindowMessage and EndSessionMessage reference types (sealed class), or pass a mutable context object. Coordinate this with the Messages reviewer, and fix E01 in the same change.
- **BREAKING:** yes (struct to class).

### E-03

**ListenForEndSession caches the first caller's callbacks and silently ignores later ones; the cache is also not thread-safe**  
*High · BREAKING*

- **File:** ApplicationRestartManager.cs:181 (`return _endSessionObservable ??= Observable.Create(...)`) and :226
- **What:** The observable, with `onQuerySession`/`onEndSession` captured in its closure, is stored in a static field. A second call with different callbacks returns the first observable, so the new callbacks are never invoked. The field is set to null from the RefCount teardown, which races with concurrent callers because there is no lock.
- **Failure scenario:** Library A calls `ListenForEndSession()` (no callbacks) and the app later calls `ListenForEndSession(onQuerySession: SaveAndAsk)`. `SaveAndAsk` is never called.
- **Fix:** Drop the cache and the callbacks. Expose one shared `IObservable<EndSessionMessage>` (Publish/RefCount, created in a static ctor or a Lazy) and let subscribers answer through a mutable message (see E02).
- **BREAKING:** yes.

### E-04

**`WinMm.Play(byte[])` uses SND_MEMORY|SND_ASYNC on a byte[] that is only pinned for the duration of the call**  
*High · BREAKING*

### E-12

- **Where:** every library `.csproj` (`TargetFrameworks`); 62 `#if !NETSTANDARD2_0` blocks (for example the whole of `ClipboardNative.OnUpdate`, `PowerBroadcastListener`, `WindowsSessionListener`, `WinProcHandler`, `BitmapAccessor`, all pixel formats, `DisplayInfo`, `RawInputMonitor`, `DeviceNotification`).
- **What:** Any consumer that is not net48 and not `-windows` (a plain `net8.0`/`net10.0` library, or a future cross-platform Greenshot core targeting `net10.0`) resolves the netstandard2.0 asset. That asset lacks most of the reactive and monitoring API (`Dapplo.Windows.SystemState` for netstandard is nearly empty) and gives no diagnostic about it.
- **Failure:** "Type or member not found" in a `net10.0` library, even though the same package works in a `net10.0-windows` app. Code that compiles against netstandard can also bind differently at runtime.
- **Fix (pick one):**
  - Drop netstandard2.0 (BREAKING).
  - Replace it with plain `net10.0` plus `[SupportedOSPlatform("windows")]`, so the analyzer warns instead of silently removing API.
  - At minimum, document per-package which APIs are missing on netstandard.
- **BREAKING:** yes, if dropped.

### F-15

**Tests that can hang, depend on timing, or test the wrong thing**  
*Medium · needs-runtime-check*

- **Where / what:**
  - `WinEventHookTests.cs:61`: `await replaySubject.Where(...).FirstAsync()` has no timeout. If the title-change event never arrives (charmap `MainWindowHandle` is 0 before the window exists), the test run hangs.
  - `IconTests.cs:49`: starts charmap, then calls `GetTopLevelWindows().First()`, which is an arbitrary window, not charmap. It asserts that some random window has an icon. `process.Kill()` is not in a `finally`, so charmap leaks when the test fails.
  - `IconTests.cs:143-169`: `TestIcon_LoadIconMetric` catches `EntryPointNotFoundException` and passes. LoadIconMetric needs comctl32 v6, and the test exe has no manifest (the V6 check test is disabled at :102), so it probably tests nothing (needs-runtime-check).
  - `KeyboardHookTests`: hook tests use `Task.Delay(20)` as synchronization. On a loaded CI runner the LL hook callback can be later than that.
  - `InputTests.cs:28-49`: `LastInputTimeSpan` and `LastInputDateTime` fail if any real or injected input happens within 50-100 ms, including from the other input tests (order-dependent).
  - `DisplayTest.TestScreenbounds`: compares DPI-virtualised `Screen.AllScreens` with the native `DisplayInfo`. It fails on mixed-DPI setups; the commented code acknowledges this.
  - `CitrixTests`, `Shell32Tests.TestAppBar`, `SoftwareInstallationTests`: assume a non-Citrix desktop with a taskbar and installed software.
  - `WindowsEnumeratorTests.EnumerateWindowsAsync_Find`: the `Form` is never closed or disposed.
- **Fix:**
  - Add `.Timeout(TimeSpan.FromSeconds(5))` and use `TestContext.Current.CancellationToken`.
  - Find the charmap window by process id.
  - Use `try/finally` around `Kill`.
  - Replace delays with `TaskCompletionSource` plus a timeout.
  - Mark environment-dependent tests as Interactive (F-06).
- **BREAKING:** no.

### F-40
